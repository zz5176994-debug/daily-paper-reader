## Abstract 

Large language models (LLMs) rely on long-horizon tool invocation sequences for complex tasks, where each invocation can alter the task state and condition subsequent decisions. In long-horizon tool use, final-outcome rewards provide weak credit assignment over long interaction traces. Step-level rewards can offer more targeted feedback, but obtaining reliable step supervision often requires human or LLM judgment, or additional rollouts to estimate the downstream effect of an intermediate decision. In this paper, we argue that effective tool-use agents should estimate the long-horizon value of a possible next tool invocation before executing it. This objective requires comparative supervision over alternative invocations under the same context, while logged trajectories only contain the invocation that was actually taken. Therefore, we propose Comparative Inference for Tool-use Agents (CITA). CITA trains a Comparative Inference Model (CIM) from paired signals that combine observed tool behavior, scalable supervision from a Bayesian tool-graph simulator, and semantic judgments from LLM-based comparison. The resulting CIM learns to estimate how likely a possible next tool invocation is to support final task success under the current context. Across three tool-use benchmarks and multiple backbone LLMs, CITA consistently improves Tool F1 and task success. Additional analysis shows that CIM learns accurate step-level value estimates for comparative tool choices. 

## 1 Introduction 

Large language models (LLMs) extend their capabilities through external tools, including search engines [1–3], calculators [4–7], code interpreters [8], and application programming interfaces (APIs) [9]. These tools extend LLMs beyond text-only generation and enable agents to interleave reasoning with action in real tool environments [10–13]. As tool use moves from isolated calls to long interaction traces, tool selection becomes a sequential decision problem [14–17]. Each tool invocation updates the task state, and an early choice can enable or block later calls [18–21]. Therefore, the quality of a tool choice cannot be judged only by its local fit to the current instruction. It also depends on whether the choice supports final task success after the remaining interaction [22–24]. This long-horizon dependency makes reinforcement learning (RL) difficult [25–27]. Final-outcome rewards are easy to define, but they provide feedback only after the full trajectory is completed. For long interaction traces, such rewards give little information about which intermediate tool invocations caused success or failure [28, 29]. Step-level rewards can provide more direct feedback, and process reward models have been studied for improving multi-step reasoning [30, 31]. However, reliable

Human annotation does not scale [32, 25, 26], and LLM-based judgments can be unstable [33, 34]. Rollout-based estimation can infer the value of an intermediate decision, but it must continue the interaction from that state and execute additional tool invocations [35, 30]. Since each continuation may update the environment state, the resulting signal is costly and noisy [28]. These concerns are visible in our pilot analysis, as shown in Figure 1. The error accumulation analysis shows that task success drops sharply as the required number of tool invocations increases, indicating that errors accumulate across long interaction traces and make local tool selection unreliable. The failure recoverability analysis shows that 95% of failed trajectories remain unrecoverable after one step of backtracking, and 76% remain unrecoverable after four steps. This suggests that final feedback often arrives too late to guide the intermediate decisions that caused failure. The first two results indicate that a tool-use agent should evaluate a possible next tool invocation before execution. The remaining question is whether the agent’s own local preference can serve as this evaluation signal. Our preference misalignment analysis shows that, at 49% of fork points, the tool ranked higher by the model has a lower empirical success rate than an alternative under the same context. This mismatch suggests that local preference alone is not sufficient for next-tool selection. These observations shift the objective from following local preference to estimating the downstream value of each possible next tool invocation. We define this signal as the long-horizon value under the current context, which measures whether a candidate invocation is likely to support final task success. Since this value is meaningful for decision making only relative to available choices, the agent must learn to compare alternative invocations under the same context. A practical obstacle is that logged trajectories only contain the invocation that was actually selected, leaving the values of unselected alternatives unobserved [36–38]. This missing comparison signal motivates a comparative inference model that learns from paired evidence over alternative tool choices. To instantiate this idea, we propose Comparative Inference for Tool-use Agents (CITA). CITA trains a Comparative Inference Model (CIM) to estimate and compare the long-horizon values of candidate next-tool invocations under the current context. Given a tool-use context and a candidate invocation, CIM predicts whether this choice is likely to support final task success. To make this comparative value signal learnable, we construct paired training signals that expose alternative choices under related or shared contexts from three complementary sources: (1) Real trajectories supply pairs by matching similar decision contexts, comparing different next tools, and using their downstream outcomes as supervision. (2) A Bayesian simulator over the tool transition graph supplies scalable pairs in a sandbox, where synthetic tool success probabilities and transition reliability probabilities are sampled from Bayesian priors. This source creates controlled fork-point comparisons without executing real APIs. (3) LLM-based comparison supplies semantic pairs by comparing the factual tool choice with a plausible alternative under the same context. These complementary signals train CIM to estimate the long-horizon value of a possible next tool invocation under the current context. CITA uses CIM as both a rollout guide and a training signal. During policy optimization training, the policy samples a set of possible next tool invocations at each decision step, and CIM selects the call 2with the highest predicted success value under the current context. This process produces complete trajectories guided by step-level value estimates. After execution, CIM scores the realized tool sequence by estimating V (st, a t) at each step, and the aggregated scores form a comparative reward. This reward is combined with a task-level matching reward to compute group-relative advantages for policy optimization. At inference, CITA reuses the same CIM-guided selection process without policy updates. This design enables CIM to guide local tool choices during trajectory construction and provide long-horizon value feedback during policy learning. We evaluate CITA on Toolathlon, TOUCAN, and TRAJECT-Bench with multiple backbone LLMs. CITA improves Tool F1 and end-to-end task success across benchmarks. We also evaluate CIM directly and show that it produces accurate step-level value estimates under comparative tool choices. Our contributions are summarized as follows: • We design a Comparative Inference Model (CIM) for long-horizon tool use and train it with a three-source data construction strategy. The strategy builds paired signals from real trajectories, a Bayesian tool-graph simulator, and LLM-based comparison. • We propose Comparative Inference for Tool-use Agents (CITA), a framework that uses CIM to guide policy optimization training. CIM scores sampled next-tool invocations during rollout generation and provides dense step-level comparative rewards after rollout completion. • We show that CITA improves Tool F1 and end-to-end task success on three tool-use benchmarks, and that CIM learns effective step-level value estimates. 

## 2 Related Work 

Prompting and Search-Based Tool Use. Prompting and search-based methods improve tool use by guiding LLMs to plan, call tools, and revise decisions based on observations [39–42]. ReAct interleaves reasoning traces with actions [10], while Toolformer trains models to decide when and how to call APIs through self-supervised data construction [4]. ToolLLM builds ToolBench and uses decision-tree search to collect tool-use trajectories over real APIs [12]. ToolChain* formulates API calling as action-space search and uses A* search to find efficient tool-use paths [43]. ART automatically composes reasoning and tool-use programs [44], ReWOO separates planning from tool execution [45], Gorilla improves API calling through fine-tuning and retrieval over API documents [9], and RestGPT applies coarse-to-fine planning to real RESTful APIs [46]. Their main limitation lies in scalability to long-horizon settings: prompting relies on local model decisions, search becomes costly as the trajectory grows, and trace-based learning is constrained by the coverage of paths. 

Reinforcement Learning and Step-Level Rewards for Tool Use. Reinforcement learning methods aim to improve tool-use policies beyond supervised imitation. GRPO estimates group-relative advantages from sampled responses without training a separate critic [47]. ToolRL studies reward design for tool selection and tool application [26]. StepTool introduces step-grained reward shaping and optimization for multi-step tool learning [25]. ReTool uses outcome-driven RL with real-time code execution to teach models when and how to use tools [48]. Tool-Star combines tool-integrated data synthesis with multi-tool self-critic RL for collaborative tool reasoning [27]. AWPO integrates explicit reasoning rewards into a GRPO-style framework through advantage weighting [49]. PORTool builds tree-like tool-use rollouts and assigns rewards to intermediate steps for fork-relative policy optimization [50]. These methods show that finer-grained feedback can improve tool learning. However, their step-level signals often depend on rules, annotations, LLM judgments, or rollout estimates, which can be costly or noisy in executable tool environments. 

Predictive and Comparative Planning for Interactive Agents. Another line of work evaluates possible actions before execution. DyMo augments function calling with state prediction in stateful tool-use environments [51]. WebDreamer simulates candidate web actions and evaluates the simulated outcomes before acting [52]. The World Knowledge Model provides global task knowledge and local dynamic knowledge for agent planning [53]. WebCoT studies web-agent skills such as lookahead, branching, reflection, and rollback [54]. LUMINA analyzes long-horizon interactive agents with an oracle comparative framework [55]. These works highlight the benefit of reasoning about an action before it is executed. CITA follows this direction but focuses on the decision itself: it estimates the long-horizon value of possible next-tool invocations under the current context, without requiring full future-state prediction or oracle skills. 33 Method 

3.1 Problem Formulation 

We consider a long-horizon tool-use task where an LLM agent solves a user request by executing a sequence of external tool invocations. Let q denote the user query. A completed trajectory is written as τ = ( q, a 1, o 1, . . . , a T , o T , y ), where at is the tool invocation at step t, ot is the tool output, and 

y ∈ { 0, 1} indicates whether the trajectory solves the task. At step t, the agent observes the current context st = ( q, a <t , o <t ), selects a possible next tool invocation at, receives ot, and updates the context. The goal is to choose tool invocations that maximize final task success. We define the long-horizon value of a possible next tool invocation as 

V ⋆(st, a ) = Pr( y = 1 | st, a ), (1) which measures how likely the task is to be completed if the agent chooses a under st. This value is not a one-step transition score. It summarizes how the current tool choice affects the remaining interaction and final outcome. If V ⋆(st, a ) were available for all possible next tool invocations, the agent could compare alternatives under the same context and choose the one with the highest long-horizon value. In logged trajectories, however, only the executed tool invocation is observed, and the values of unselected alternatives are missing. CITA addresses this challenge by learning an estimator Vϕ(st, a ) with a comparative inference Model (CIM). Since the target value concerns choices that are not jointly observed in a single trajectory, CIM is trained on paired signals instead of isolated trajectory labels. 

3.2 Training Signals for CIM 

Each paired signal compares two possible next-tool choices under a comparable context: 

x = ( s, a f , a c, v f , v c, ∆v), ∆v = vf − vc, (2) where s is the tool-use context, af and ac are two alternative next-tool invocations, and vf and vc are their estimated long-horizon success values. These pairs train CIM to estimate the value of each tool invocation and compare two choices under the same context. CITA also builds a tool transition graph from logged trajectories. Each node is a tool, and each directed edge records an observed transition between two tools. The graph is used to identify plausible next-tool choices and to support the Bayesian simulator. 

Dobs : observed trajectory pairs. The first source comes from real tool-use trajectories. CITA groups logged episodes by task and decision context, where the context includes the prefix tool sequence and compact summaries of recent arguments and outputs. For each context s and next tool a, its empirical value is estimated as the downstream success rate ˆvobs (s, a ) = Nsucc (s, a )/N (s, a ). For two tools observed under the same context, we set vf = ˆ vobs (s, a f ), vc = ˆ vobs (s, a c), and ∆v = vf − vc.This source keeps the training signal close to real tool-use behavior, but its coverage depends on the diversity of logged trajectories.

It creates synthetic sandbox instances where each tool node receives a sampled success probability and each transition edge receives a sampled reliability probability. 3.3 Architecture of the Comparative Inference Model 

The role of CIM is to estimate the long-horizon value of a possible next tool invocation under the current tool-use context. Given a context s and a candidate tool invocation a, it outputs a value estimate Vϕ(s, a ) ∈ [0 , 1] and a confidence score cϕ(s, a ) ∈ [0 , 1] . The value estimate predicts how likely choosing a under s is to support final task success, while the confidence score measures the reliability of this estimate. 5The model first encodes the textual information in the tool-use state, including the user query, previous tool invocations, tool outputs, and the candidate tool. We use the LLM backbone as a semantic encoder and project its hidden states into a lower-dimensional space for value estimation. A context encoder summarizes the current tool-use state into hs, and an action encoder maps the candidate tool into ha.A scoring module combines hs and ha into a decision representation: 

zs,a = gϕ(hs, h a), Vϕ(s, a ) = σ(fv (zs,a )) , cϕ(s, a ) = σ(fc(zs,a )) . (5) Here gϕ is the scoring module, fv and fc are the value and confidence heads, and σ(·) is the sigmoid function. The two heads use the same decision representation but learn different targets. In implementation, the confidence head reads a detached representation, so confidence calibration does not directly interfere with value learning. CIM uses paired forward computation during training. For a paired signal x = ( s, a f , a c, v f , v c, ∆v),the context s is encoded once and shared by both choices: 

ˆvf = Vϕ(s, a f ), ˆvc = Vϕ(s, a c), ∆ˆ v = ˆ vf − ˆvc. (6) This design lets the model learn both the value of each possible next tool invocation and the value gap between two choices under the same context. At inference time, CIM uses the single-call form 

Vϕ(s, a ) and cϕ(s, a ) to score candidate tool invocations. 

3.4 CIM Training 

CIM is trained to learn two abilities: estimating the value of a possible next tool invocation and comparing two choices under the same context. For a pair x = ( s, a f , a c, v f , v c, ∆v), CIM produces 

ˆvf , ˆvc, and ∆ˆ v as defined in Eq. 6. We first supervise the value estimates with 

Lvalue = 12 [BCE(ˆ vf , v f ) + BCE(ˆ vc, v c)] . (7) This term teaches CIM to predict the long-horizon success value of each tool choice. To make pairwise comparison explicit, we further match the predicted value gap to the paired label: 

Lgap = (∆ˆ v − ∆v)2. (8) This term is central to comparative value estimation, because the agent must decide which choice is better under the same context. We add two auxiliary objectives. The consistency loss Lcons regularizes value gaps with self-identity and transitivity constraints. The confidence loss Lconf calibrates the confidence head using pseudo-labels derived from prediction errors, so that low-error estimates receive higher confidence. The final objective is 

LCIM = Lvalue + αLgap + βLcons + γLconf . (9) We use a progressive training schedule. CIM first learns stable value prediction, then incorporates pairwise gap and consistency objectives, and finally calibrates confidence for rollout guidance and reward aggregation.

## 4 Experiments 

4.1 Setup Benchmarks. We evaluate CITA on three long-horizon tool-use benchmarks: Toolathlon [22], TOUCAN [23], and TRAJECT-Bench [24]. These benchmarks cover different types of tool-use difficulty. Toolathlon focuses on long-horizon dependency with about 13.5 tool invocations per episode. TOUCAN has shorter trajectories, about 3.2 calls per episode, but a large tool pool of 15,294 unique tools. TRAJECT-Bench provides a medium-horizon setting with about 6.4 tool invocations per episode and 715 unique tools. Appendix A provides detailed statistics. 

Backbone models. We report results with Qwen2.5-7B [56] and Llama3.1-8B [57]. Both models are first adapted to the tool-use format with supervised fine-tuning, and then optimized with the corresponding training method. 

Baselines. We compare CITA with baselines from three categories. The first category includes prompting and search-based tool-use methods, including ReAct [10], ToolChain* [43], and ToolLLM [12]. The second category includes reinforcement learning and step-level reward methods, including ToolRL [26], StepTool [25], AWPO [49] , IPR [58], and AgentPRM [31]. The third category includes predictive and planning-based methods, including DyMo [51], WebDreamer [52], and WKM [53]. 

Metrics. We use Tool F1 and Task Success Rate as the primary metrics. Tool F1 evaluates whether the generated trajectory selects the correct tools compared with reference trajectories, while Task Success Rate evaluates whether the completed trajectory solves the task. The former reflects tool-selection quality, and the latter reflects end-to-end task completion. For Task Success Rate, we send the full tool-use process, including tool invocations and observations, to GPT-4o and use the same evaluation prompt for all methods.

4.3 CIM Value Estimation Quality 

We next evaluate whether CIM learns effective comparative value estimates for tool choices. Given a held-out paired example, CIM predicts the value gap ∆ˆ v between the factual tool choice and an alternative tool choice. We evaluate this prediction from three aspects. Value Gap MAE measures the absolute error between ∆ˆ v and the observed value gap ∆v. Direction Accuracy measures whether the sign of ∆ˆ v matches the sign of ∆v, which indicates whether CIM selects the better tool choice. These results show that the full objective helps CIM estimate value gaps and identify the better tool choice. ## 5 Conclusion and Limitations 

This paper introduced CITA, a comparative inference framework for long-horizon tool use in LLM agents. CITA trains a Comparative Inference Model to compare candidate next-tool invocations under the current context and estimate their long-horizon value. The model is learned from paired signals built from real trajectories, a Bayesian tool-graph simulator, and LLM-based comparison, and is used to guide GRPO training and inference. Across three benchmarks, CITA improves Tool F1 and Task Success Rate. Value-estimation analysis and ablations further show that CIM learns meaningful value gaps. The current study focuses on benchmarked tool environments with available logged trajectories and tool graphs, which provides a controlled setting for evaluating comparative value estimation. ## C Additional CIM Value Estimation Results 

This section provides additional details for the CIM value estimation evaluation. The goal is to test whether CIM can predict the value difference between two next-tool choices under the same or comparable context. For each held-out pair, CIM predicts ∆ˆ v = ˆ vf − ˆvc, and we compare it with the observed value gap ∆v. The evaluation set is built from observed trajectory pairs with sufficient support. Following the evaluation protocol, we separate strong-effect pairs and near-neutral pairs by the magnitude of the observed value gap. Strong-effect pairs satisfy |∆v| ≥ 0.15 , while near-neutral pairs satisfy |∆v| ≤ 0.05 . This split allows us to evaluate not only numerical value-gap estimation, but also whether CIM can distinguish meaningful tool-choice differences from weak or negligible differences. 

Core metrics. The main text reports three metrics. Value Gap MAE measures the mean absolute error between the predicted and observed value gaps, |∆ˆ v − ∆v|. It evaluates whether CIM estimates the size of the value difference correctly. Direction Accuracy measures whether ∆ˆ v and ∆v have the same sign. It evaluates whether CIM identifies which tool choice has the higher long-horizon value. This metric is directly related to decision making, because the agent usually needs to choose the better tool rather than predict the exact value gap. AUROC evaluates whether the magnitude 

|∆ˆ v| can distinguish strong-effect pairs from near-neutral pairs. It measures whether CIM assigns larger predicted gaps to pairs where the two tool choices truly differ. 

Additional discrimination metrics. We also report AUPRC and CvS . AUPRC uses the same score |∆ˆ v| as AUROC, but focuses on the precision-recall tradeoff for identifying strong-effect pairs. It is useful when the number of strong-effect and near-neutral pairs is imbalanced. CvS, short for contrast-vs-small-gap score, measures whether strong-effect pairs receive predicted gaps above a fixed threshold and near-neutral pairs receive predicted gaps below the threshold. In our evaluation, the threshold is 0.1. A high CvS means that CIM not only detects meaningful differences, but also avoids assigning large gaps to near-neutral comparisons. 

Correlation metrics. Pearson and Spearman correlations measure agreement between predicted and observed value gaps from two complementary views. Pearson r measures linear agreement between ∆ˆ v and ∆v. It is high when the predicted gap increases proportionally with the observed gap. Spearman r measures rank-level agreement. It is high when CIM orders pairs by value-gap strength in a way that matches the observed ordering, even if the exact scale is not perfectly calibrated. The additional metrics support the conclusion in the main text 2. On TOUCAN, Full CIM greatly improves CvS from 0.2667 to 0.9333 and increases Pearson correlation from 0.7652 to 0.9004, indicating that the complete objective produces value gaps that are better calibrated and more discriminative. AUPRC is already high for CIM w/ Lvalue only and remains high for Full CIM, which suggests that this dataset is already separable under the AUPRC metric. ## E Implementation Details 

This section provides implementation details for the experiments. Additional details on paired data construction are provided in Appendix F. Unless otherwise specified, all experiments use the same train-test split, tool environment, and evaluation protocol across methods. 

Backbone models. We use Qwen2.5-7B and Llama3.1-8B as backbone LLMs. Both models are first adapted to the tool-use format with supervised fine-tuning and then optimized with the corresponding training method. The same tokenizer, tool registry, simulator, and evaluation scripts are used for all methods. 

Tool-use format. All models follow a unified tool invocation format. The system prompt lists the available tools for the current task and requires the model to emit a structured invocation: 

<tool_call>{"name": "...", "arguments": {...}}</tool_call> .

After each invocation, the tool response is appended to the dialogue context, and the model either invokes another tool or produces a final response. For each task, we include tools from successful reference trajectories, add related tools, and fill the remaining slots with randomly sampled tools. We use at most 50 tools in the prompt. 

Supervised fine-tuning. SFT data are constructed from successful tool-use episodes. Each example is formatted as a multi-turn dialogue containing the user request, tool invocations, tool responses, 17 and the final response. We also include continuation examples that start from intermediate trajectory prefixes, exposing the model to partially completed tool-use states. SFT is performed with LoRA and assistant-only loss masking, where loss is computed only on assistant outputs. For the 7B and 8B backbones, we use LoRA rank 64, LoRA alpha 128, learning rate 5 × 10 −6, maximum sequence length 4096, and train for 3 epochs. 

CIM training. CIM is trained after SFT and before GRPO. The model uses the LLM backbone as a semantic encoder and projects hidden states into a lower-dimensional value-estimation space. In our main configuration, the CIM hidden dimension is 768, and the CIM module uses 8 Transformer layers with 12 attention heads. The final decision representation is passed to two lightweight MLP heads: a value head for Vϕ(s, a ) and a confidence head for cϕ(s, a ). The training objective follows Eq. 9. We train CIM with a progressive schedule that gradually increases the difficulty of supervision. In the first stage, we activate only Lvalue , so the model learns stable estimates of Vϕ(s, a ) before being asked to compare alternatives. In the second stage, we add Lgap and Lcons , which trains CIM to match value differences between paired tool choices and regularizes the comparison space with self-identity and transitivity constraints. In the final stage, we add Lconf to calibrate the confidence head after the value estimates have become stable. This schedule avoids forcing value prediction, pairwise comparison, and confidence calibration to be learned from scratch at the same time. For CIM training, we use batch size 8, gradient accumulation 8, backbone learning rate 1 × 10 −5, CIM learning rate 5 × 10 −5, and AdamW optimization with a warmup-cosine learning-rate schedule. 

GRPO training. For CITA, we initialize the policy from the SFT model and optimize it with CIM-guided GRPO. The SFT LoRA adapter is merged into the base model, and a new trainable actor LoRA adapter is attached for GRPO. The trained CIM is kept frozen during policy optimization and is used to score candidate tool invocations and compute comparative rewards. We use LoRA rank 64, LoRA alpha 128, learning rate 2 × 10 −6, group size 6, gradient accumulation 2, sampling temperature 0.7, and maximum rollout length 15. The reward is the weighted combination in Eq. 13, with wtask = 0 .4 and wcmp = 0 .6.

CIM-guided rollout and inference. During GRPO rollout generation, the policy samples multiple candidate tool invocations at each decision step. In the main setting, we sample 3 candidates per step. CIM scores each candidate using Eq. 10, and the highest-scoring invocation is executed. The returned observation is appended to the context before the next step. Inference uses the same CIM-guided selection rule as rollout generation, but no policy update is performed. 

Data split and reproducibility. We use a deterministic task-level split with seed 42. Test tasks are excluded from SFT continuation construction and GRPO prompt sampling. For datasets where task names are not unique enough to define tasks, we use the user prompt as the task key. All reported results use the same held-out split across methods. 

Hardware and precision. We train 7B and 8B models with mixed precision and gradient check-pointing. SFT uses HuggingFace Trainer and DeepSpeed ZeRO-2 when needed. GRPO uses a custom training loop with a shared base LLM, a trainable actor LoRA adapter, and a frozen CIM module. Main experiments are run on 8x H100 GPUs.

F.5 Train-Validation Split and Leakage Control 

We use a group-aware split when creating CIM train and validation sets. The split key includes the source, task identifier, context prefix, argument-pattern hashes, and recent output signatures. For sandbox pairs, the split key also includes the sandbox identifier and context. We further group mirror comparisons by sorting the factual and comparative action identifiers. This prevents a pair (af , a c)

from appearing in training while its mirrored comparison (ac, a f ) appears in validation under the same context. This split is important because paired comparisons often come in symmetric or closely related forms. A naive random split could leak the same state family into both train and validation sets, leading to overestimated value-estimation quality. The group-aware split keeps related comparisons in the same split and provides a more reliable validation signal for CIM. 

## G Evaluation Protocol 

This section describes the general evaluation protocol used in our experiments. The GPT-4o judge protocol for Task Success Rate is provided separately in Appendix H. All methods are evaluated on the same held-out split, with the same tool registry, tool simulator, maximum step budget, and evaluation prompts. 

Held-out split. We use a deterministic task-level split with seed 42. For datasets with meaningful task names, the task name is used as the split key. For datasets where task names are not sufficiently discriminative, we use the user prompt as the task key. We assign 20% of task keys to the test split by hashing the task key with the seed. Test tasks are excluded from GRPO prompt sampling and training-time trajectory construction. 

Trajectory collection. For each test task, the agent interacts with the same tool simulator. At each step, the model emits a structured tool invocation: 

<tool_call>{"name": "...", "arguments": {...}}</tool_call> .

21 The simulator returns the corresponding observation, which is appended to the dialogue context. The interaction terminates when the model produces a final response or reaches the maximum step limit. We record the user request, all tool invocations, tool arguments, tool observations, and the final response. 

Tool-name normalization. Before computing tool-matching metrics, we normalize tool names by removing version suffixes such as _v1 or _v13 . We also ignore minor formatting differences such as case, hyphen, and underscore variations when the normalized tool names indicate the same function. 

Tool F1. Tool F1 evaluates whether the generated trajectory selects tools that match successful reference trajectories. Let P = ( p1, . . . , p m) be the generated tool sequence and R = ( r1, . . . , r n)

be a reference sequence. We compute an order-preserving fuzzy match between normalized tool names and denote the number of matched invocations by M (P, R ). Precision, recall, and F1 are computed as 

Precision = M (P, R )

|P | , Recall = M (P, R )

|R| , F1 = 2 · Precision · Recall Precision + Recall . (22) When multiple successful reference trajectories are available for a task, we compute Tool F1 against each reference and use the best score. This avoids penalizing a model when it follows a valid alternative tool path. 

Additional metrics. Besides Tool F1 and Task Success Rate, we compute several diagnostic metrics. 

Next-tool Accuracy measures whether the predicted next tool matches the reference next tool under a given context. Average Steps reports the average number of generated tool invocations. Progress Rate measures the fraction of examples where the model invokes at least one tool. Argument Quality evaluates whether generated tool arguments are compatible with the selected tool schema and historical observations. These metrics are used for diagnostics and are reported in Appendix J. 

Aggregation. For each method, we aggregate metrics over all valid held-out episodes. Tool F1, Next-tool Accuracy, Argument Quality, Progress Rate, and Task Success Rate are reported as percentages unless otherwise specified. For tables that average across settings, we first compute each metric within one dataset-backbone setting and then take the arithmetic mean over the six settings.

## I Baseline Details 

This section describes how we adapt baseline methods to our long-horizon tool-use setting. All baselines are evaluated with the same held-out split, tool registry, tool simulator, maximum step budget, and evaluation protocol as CITA. For fair comparison, all trainable baselines start from the same SFT-initialized backbone used by CITA. Prompting and search-based baselines use the same tool invocation format and tool list. RL-based baselines use the same rollout budget and GRPO implementation unless the original method specifies a different optimization rule. Predictive and planning-based baselines use the same candidate generation budget as CITA whenever candidate-level comparison is required. 

I.1 Prompting and Search-Based Tool Use ReAct. ReAct interleaves natural-language reasoning with tool actions. We implement ReAct by adding a method-specific instruction that asks the model to alternate between a short reasoning step and a structured tool invocation. The tool invocation is still required to follow the same format used by all methods: 

<tool_call>{"name": "...", "arguments": {...}}</tool_call> .

After each tool observation, the model updates its reasoning state and either invokes another tool or produces a final answer. No CIM score or comparative reward is used. 

ToolChain*. ToolChain* formulates tool use as action-space navigation and applies A* search to find a low-cost tool-use path. We adapt this idea by building a search tree over candidate tool invocations. Each node represents a partial tool-use trajectory, and each outgoing edge corresponds to a possible next tool invocation generated by the policy. We score each partial path with a cost that combines model generation cost, tool-name validity, argument validity, and task-progress heuristic. The search keeps a fixed frontier size and expands candidates until the model terminates or reaches the maximum step limit. The same tool simulator is used to execute expanded tool invocations. This baseline tests whether explicit search over tool-use paths can replace CIM-based value estimation. 

ToolLLM. ToolLLM provides a general framework for tool-use data construction, model training, and tool invocation evaluation. Since the original ToolLLM uses ToolBench and its own tool environment, we implement a ToolLLM-style baseline in our benchmark environment. The model is initialized from the same SFT checkpoint and uses the same tool descriptions. At inference time, we use a decision-tree search strategy over generated tool invocations, following the ToolLLM setting where the agent explores tool-use trajectories and selects a valid execution path. The search budget, maximum step limit, tool formatting rules, and simulator are matched to the other methods. 24 I.2 Reinforcement Learning and Step-Level Reward Baselines ToolRL. ToolRL studies reward design for tool learning under reinforcement learning. We adapt ToolRL by training the SFT policy with GRPO using tool-use rewards that do not include CIM. The reward contains task-level trajectory matching, tool validity, and argument validity terms. This baseline uses the same rollout generation budget and held-out split as CITA, but it does not compare comparative next-tool choices under the same context. 

StepTool. StepTool introduces step-grained reinforcement learning for multi-step tool use. We implement this baseline by adding step-level rewards derived from reference tool trajectories. At each step, the model receives feedback based on whether the selected tool matches the corresponding reference step or supports progress toward a reference trajectory. The step-level rewards are aggre-gated with the task-level reward for GRPO training. Unlike CITA, StepTool does not train a separate comparative value model and does not score alternative candidate invocations before execution. 

IPR. IPR performs iterative step-level process refinement by estimating step-level rewards and using them to improve agent behavior. We adapt IPR by generating alternative actions along reference prefixes and evaluating them with rollout-based or reference-based feedback. The resulting step-level comparisons are used to refine the policy iteratively. To keep the comparison fair, IPR uses the same SFT initialization, tool simulator, maximum step budget, and rollout budget as CITA. The key difference is that IPR estimates process feedback through iterative refinement, whereas CITA trains CIM to directly estimate the long-horizon value of possible next-tool invocations. 

AWPO. AWPO integrates reasoning-related reward signals into policy optimization through adap-tive advantage weighting. We adapt AWPO by combining the task-level reward with auxiliary reasoning and format rewards, then applying advantage weighting during GRPO training. The reasoning reward encourages coherent task decomposition and valid tool-use planning, while the format reward encourages valid structured tool invocations. No CIM score, Bayesian simulator pair, or LLM-based comparative pair is used in this baseline. 

AgentPRM. AgentPRM trains a process reward model for agent decisions by modeling both promise and progress. We adapt AgentPRM by training a step-level reward model from the same logged trajectories used in our experiments. The reward model scores intermediate tool-use states and candidate actions according to their estimated progress toward task completion. During policy optimization, AgentPRM scores are used as step-level rewards or candidate-ranking signals. This baseline evaluates whether a general process reward model for agents can substitute for CIM. Unlike CIM, AgentPRM is not trained on the three-source paired comparative construction and does not explicitly match value gaps between alternative tool invocations under the same context. 

I.3 Predictive and Planning-Based Baselines DyMo. DyMo learns an internal environment model for stateful tool use by combining function calling with state prediction. We adapt DyMo by adding a state-prediction objective to the SFT policy. After each tool invocation, the model predicts a compact summary of the resulting state before observing or using the next tool. At inference time, candidate invocations are ranked according to their predicted state progress and tool validity. This baseline tests whether implicit state-dynamics prediction can provide enough lookahead for long-horizon tool selection. 

WebDreamer. WebDreamer uses an LLM as a world model and value function to simulate outcomes of candidate actions before execution. We adapt this idea by prompting an LLM planner to imagine the likely observation and task progress after each candidate tool invocation. The imagined outcomes are then scored, and the highest-scoring candidate is executed in the real tool simulator. The number of candidates and the maximum step budget are matched to CITA. Unlike CITA, WebDreamer-style planning relies on natural-language outcome simulation at inference time rather than a trained CIM that directly estimates next-tool value. 

WKM. WKM provides global task knowledge before execution and local dynamic knowledge during agent planning. We adapt WKM by first generating a task-level knowledge summary that describes likely subtasks, relevant tools, and expected intermediate states. During execution, the 25 model updates a local state summary after each tool observation and conditions the next tool invocation on both the global and local knowledge. This baseline tests whether explicit planning knowledge can improve tool-use trajectories without learning a comparative value estimator. 

I.4 Fairness and Budget Control 

For all baselines, we control the following factors. First, all methods use the same tool registry and the same per-task tool list construction. Second, all generated tool invocations are executed by the same simulator and are subject to the same maximum step limit. Third, trainable methods use the same SFT initialization and held-out split. Fourth, methods that require candidate comparison use the same candidate budget as CITA whenever possible. Finally, all methods are evaluated with the same Tool F1 computation and the same GPT-4o judge protocol for Task Success Rate. These controls ensure that performance differences mainly reflect the baseline method rather than differences in backbone, tool access, evaluation, or decoding budget.

## K Confidence Calibration of CIM 

We further evaluate whether the confidence head of CIM produces a meaningful reliability estimate. In our method, the confidence score cϕ(s, a ) is used together with the value estimate Vϕ(s, a )

during candidate scoring and reward aggregation. This experiment tests whether a higher predicted confidence indeed corresponds to a higher empirical prediction accuracy. For each held-out context-action pair (s, a ), we record the predicted value Vϕ(s, a ) and confidence score cϕ(s, a ). We convert the value prediction into a binary success decision by thresholding at 0.5. That is, the model predicts success when Vϕ(s, a ) > 0.5, and predicts failure otherwise. This binary prediction is then compared with the ground-truth binary label to determine whether the prediction is correct. To evaluate calibration, we partition all examples into 10 bins according to the predicted confidence, from [0 , 0.1) to [0 .9, 1.0] . For each bin, we compute the average confidence and the empirical accuracy. A perfectly calibrated model should satisfy that the average confidence matches the empirical accuracy in each bin. We summarize calibration quality using Expected Calibration Error (ECE), defined as

Instead, it learns a useful reliability signal that better reflects whether a value prediction is likely to be correct. This finding is consistent with the ablation results in the main text, where removing confidence-based scoring leads to lower Tool F1 and task success.

Offline cost. CITA also introduces offline costs for paired data construction and CIM training. The Bayesian simulator pairs are inexpensive because they are generated on the tool transition graph without executing real APIs. At inference time, CITA does not call an LLM judge or perform LLM-based comparative rollout imagination. It only uses the trained CIM to score candidate invocations. This amortizes the cost of comparative supervision and keeps online inference substantially cheaper than planning methods that simulate future states at every decision step. 

Scalability. The main online overhead of CITA scales linearly with the number of sampled can-didates K and the number of decision steps. In practice, we use a small candidate budget, K = 3 ,which is sufficient to provide alternatives for CIM comparison while keeping latency moderate. The K = 1 ablation in Appendix D shows that removing candidate comparison hurts performance, confirming that a small amount of additional computation is useful for long-horizon tool selection.

## N Broader Impact and Responsible Use 

CITA aims to improve the reliability of long-horizon tool-use agents by helping them compare candidate next-tool invocations before execution. More reliable tool selection may reduce unnecessary invocations, improve task completion, and make agent behavior easier to inspect through value and confidence scores. At the same time, stronger tool-use agents should be deployed with appropriate safeguards. External tools may access files, APIs, databases, or other stateful environments, where incorrect invocations can have undesirable effects. CITA improves decision quality, but it does not replace environment-level safety controls. For real deployment, tool permissions, sandboxing, rate limits, execution logs, and human confirmation for irreversible or high-impact actions remain important. 30 Our experiments are conducted in benchmarked tool environments rather than real-world high-stakes deployments. For broader use, CIM-guided tool selection should be combined with policies that restrict sensitive tools, validate arguments before execution, and monitor agent behavior over time. 31
